# Production Distributed Leadership Election Design

## 1. Executive Summary

HPActor cluster singletons need a production-grade leadership contract before
they can safely own mutating control-plane roles such as `ShardCoordinatorActor`,
cluster pub-sub mediation, receptionist coordination, or global schedulers.

The current singleton election seam (`ISingletonElection`) is useful for local
policy selection, tests, and deterministic fallback behavior. It is not enough
for production leadership because local alive-node views, in-memory votes, and
locally incremented fencing tokens cannot prove that only one node may mutate
cluster metadata during a partition.

This design introduces a distributed leadership layer with a production default:

- **External coordinator first**: etcd is the preferred first backend; Consul is
  supported through the same adapter contract.
- **Internal Raft later**: HPActor can add an in-process Raft backend without
  changing singleton and shard-coordinator consumers.
- **Backend-issued fencing**: mutating cluster actions use a monotonically
  ordered fencing token from the backend, not a local counter.
- **Fail closed for ownership**: if the node cannot prove it still owns the
  lease, it steps down before accepting new ownership mutations.

The core rule is simple: a cluster singleton is active only while it holds a
valid `LeadershipLease` issued by a linearizable backend. The lease token is the
only authority accepted by shard and singleton mutating paths.

## 2. Relationship To Existing Design

Existing documents remain useful, but their scope should be explicit:

- `cluster-subsystem-architecture.md` describes the cluster control plane and
  singleton integration point.
- `leader-election-design.md` describes local and gossip-assisted election
  strategies. Those strategies are not production consensus.
- This document is the production target for distributed leadership and fencing.

`OldestNodeElection`, `FixedPriorityElection`, and `MajorityBasedElection` remain
valid for deterministic tests, single-process development, and non-critical
deployments. Production singleton ownership should use the leadership backend
described here.

## 3. Goals

1. Provide exactly-one active owner semantics for mutating cluster singletons.
2. Prevent split-brain writes during node failure, restart, and network
   partition.
3. Make `ShardCoordinatorActor` leadership safe enough for production shard
   ownership updates.
4. Use an external coordinator as the first production implementation.
5. Keep an internal Raft backend possible through the same interface.
6. Preserve opt-in cluster mode and source-compatible single-node defaults.
7. Keep blocking coordinator I/O out of actor scheduler and event-loop hot paths.
8. Expose leadership state through metrics, CLI/admin, logs, and audit events.

## 4. Non-Goals

- Replacing SWIM gossip membership. Gossip remains the detector and discovery
  input, not the authority for singleton ownership.
- Implementing internal Raft in the first production milestone.
- Providing active-active singleton writes.
- Making all actor sends linearizable. This design only covers control-plane
  ownership for singleton and shard metadata mutations.
- Depending on exceptions, RTTI, or blocking work inside cooperative actor
  execution paths.

## 5. Production Contract

### 5.1 Leadership Authority

A node may act as singleton owner only if all conditions are true:

1. The node is `Alive` in `ClusterFailureModel`.
2. The node identity matches the configured `cluster_id`, `node_id`,
   incarnation, process start id, and security identity.
3. The leadership backend has granted a non-expired lease for the singleton.
4. The node can renew or validate that lease before its local safety deadline.
5. Mutating commands carry the current backend-issued fencing token.

If any condition becomes false, the node must transition to `SteppingDown` or
`NoQuorum` and stop accepting mutating singleton work.

### 5.2 Fencing Token

The fencing token is generated by the backend and must be globally ordered for a
given `(cluster_id, singleton_name)` pair.

Recommended token sources:

| Backend | Fencing Token |
|---------|---------------|
| etcd | KV `mod_revision` or committed create/update revision |
| Consul | KV `ModifyIndex`, optionally paired with a generation key |
| Internal Raft | `(term, log_index)` of the committed grant entry |

Local code never increments fencing tokens. The existing
`SingletonIdentity::fencing_token` should become a projection of the current
lease token, not an owner-local counter.

### 5.3 Fail-Closed Ownership

Leadership is fail-closed. A node that loses access to the coordinator, cannot
renew before the safety deadline, receives a higher-token owner event, or sees
its own identity fenced must stop mutating ownership metadata.

User message delivery may still follow `FailOpen` policy, but singleton and shard
ownership changes do not.

## 6. Core Types

### 6.1 LeadershipLease

```cpp
struct LeadershipLease {
    std::string cluster_id;
    std::string singleton_name;
    std::string owner_node_id;
    uint64_t owner_incarnation = 0;
    uint64_t owner_process_start_id = 0;
    uint64_t membership_epoch = 0;
    uint64_t fencing_token = 0;
    uint64_t backend_term = 0;       // Raft term or external generation.
    uint64_t backend_revision = 0;   // KV revision or Raft log index.
    Clock::time_point lease_deadline;
};
```

`fencing_token`, `backend_term`, and `backend_revision` are separate because
different backends expose different ordering fields. Consumers compare
`fencing_token`; diagnostics preserve backend details.

### 6.2 LeadershipAttempt

```cpp
struct LeadershipAttempt {
    std::string singleton_name;
    ClusterNodeIdentity self_identity;
    uint64_t observed_membership_epoch = 0;
    Clock::duration lease_ttl;
};
```

The backend rejects attempts from stale cluster ids, stale membership epochs, or
nodes that fail identity validation.

### 6.3 LeadershipStatus

```cpp
enum class LeadershipStatusCode : uint8_t {
    Granted,
    AlreadyOwned,
    Renewed,
    Released,
    Lost,
    NotOwner,
    BackendUnavailable,
    StaleMembershipEpoch,
    IdentityRejected,
    PermissionDenied,
    TimedOut,
};
```

Every non-success status maps to `FailureReason` and, where appropriate,
`FailureEnvelope` and audit records.

## 7. Backend Interface

The singleton manager should not know whether leadership comes from etcd,
Consul, or internal Raft. It depends on a narrow backend interface.

```cpp
class ILeadershipBackend {
  public:
    virtual ~ILeadershipBackend() = default;

    virtual LeadershipResult try_acquire(const LeadershipAttempt& attempt) = 0;
    virtual LeadershipResult renew(const LeadershipLease& lease) = 0;
    virtual LeadershipResult release(const LeadershipLease& lease) = 0;
    virtual LeadershipResult current_owner(std::string_view singleton_name) = 0;
    virtual void watch(std::string_view singleton_name,
                       LeadershipWatchCallback callback) = 0;
};
```

Implementation constraints:

- External coordinator clients run on a dedicated blocking/daemon executor or
  async transport abstraction. They do not run in `EventBasedActor::receive()`,
  scheduler worker loops, or event-loop callbacks.
- Calls have bounded deadlines.
- Results are explicit typed values. No exception-based control flow.
- The interface is mockable for deterministic unit tests.

## 8. Component Architecture

```text
GossipMembership
    |
    v
ClusterFailureModel -----> ClusterLeadershipManagerActor
                                |
                                v
                         ILeadershipBackend
                         /              \
              ExternalCoordinator     InternalRaftBackend
              (etcd/Consul)           (future)
                                |
                                v
                         LeadershipLease
                                |
                                v
SingletonManagerActor -----> ShardCoordinatorActor
        |                         |
        v                         v
 singleton lifecycle       token-gated mutations
```

### 8.1 ClusterLeadershipManagerCore

Thread-safe core class that owns per-singleton leadership state.

Responsibilities:

- Track local state for each registered singleton.
- Validate `ClusterFailureModel` eligibility before campaigning.
- Call `ILeadershipBackend::try_acquire()`, `renew()`, and `release()`.
- Convert backend results to local state transitions.
- Publish lease updates to `SingletonManagerActor`.
- Enter `NoQuorum` or `SteppingDown` when renewals fail.

### 8.2 ClusterLeadershipManagerActor

Actor wrapper around the core.

Responsibilities:

- Receive cluster node-state changes and membership epoch updates.
- Schedule bounded renewal ticks.
- Forward lease grant/loss events to `SingletonManagerActor`.
- Emit metrics, audit logs, and CLI snapshots.
- Keep blocking backend work outside the actor thread by delegating to the
  backend executor.

### 8.3 SingletonManagerActor Integration

`SingletonManagerActor` no longer decides production ownership by calling
`ISingletonElection::elect(alive_nodes)` directly.

Production flow:

1. `SingletonManagerActor` registers a singleton with
   `ClusterLeadershipManagerActor`.
2. `ClusterLeadershipManagerActor` obtains or watches a `LeadershipLease`.
3. If the lease owner is local, `SingletonManagerActor` transitions
   `Standby -> Activating -> Active`.
4. The singleton actor receives the `LeadershipLease` as activation context.
5. If the lease is lost or superseded, `SingletonManagerActor` transitions
   `Active -> Draining -> Standby`.

Local election strategies may still be used when
`system.cluster.leadership.mode = "local"`, but that mode is not the production
default.

### 8.4 ShardCoordinatorActor Integration

`ShardCoordinatorActor` is the first production consumer.

Every mutating command must carry:

- `singleton_name = "shard-coordinator"`
- `fencing_token`
- `membership_epoch`
- optional backend revision for audit

The coordinator rejects commands when:

- token is absent,
- token is lower than the active lease token,
- membership epoch is stale,
- owner node identity does not match the current lease,
- local node is not `Active` for that lease.

Rejected commands return `FailureReason::FencingTokenStale`,
`FailureReason::NodeUnavailable`, or a new leadership-specific failure reason
such as `LeadershipUnavailable`.

## 9. External Coordinator Backend

### 9.1 etcd Backend

etcd is the preferred first production backend because its lease, transaction,
revision, and watch APIs directly match this design.

Key layout:

```text
/hpactor/<cluster_id>/singletons/<singleton_name>/owner
/hpactor/<cluster_id>/singletons/<singleton_name>/audit/<revision>
/hpactor/<cluster_id>/membership/epoch
```

Acquire:

1. Create an etcd lease with TTL.
2. Run a transaction:
   - If owner key does not exist, put local `LeadershipLease` value.
   - If owner key belongs to this same node incarnation, refresh it.
   - Otherwise return current owner.
3. Use the committed revision or owner key `mod_revision` as `fencing_token`.
4. Start keepalive/renewal.

Renew:

1. Keep the etcd lease alive.
2. Verify the owner key still matches local identity and token.
3. If verification fails, report `Lost`.

Watch:

1. Watch the owner key from current revision.
2. On delete, compaction, higher revision, or mismatched owner value, notify the
   local manager.
3. Compacted watches force a linearizable `current_owner()` read before any new
   activation decision.

Release:

1. Best-effort delete if key still matches local identity and token.
2. Revoke lease after transition to `Draining`.

### 9.2 Consul Backend

Consul support uses sessions and KV locks.

Acquire:

1. Create a session with TTL and node identity metadata.
2. Acquire the singleton key with the session.
3. Read KV metadata and use `ModifyIndex` as the fencing token.
4. If stronger monotonicity is required across lock delete/recreate cycles, pair
   the lock with a generation key updated through CAS.

Renew:

1. Renew the session.
2. Verify the KV key still references the local session and identity.

Watch:

1. Use blocking queries on KV index.
2. Treat index rewind, session loss, or owner mismatch as lease loss.

Consul is acceptable for deployments already standardized on Consul. etcd remains
the recommended first implementation because its revision model is simpler for
fencing.

## 10. Future Internal Raft Backend

The internal Raft backend implements the same `ILeadershipBackend` interface.

Raft log entries:

```text
GrantLeadership(singleton, owner_identity, membership_epoch, ttl)
RenewLeadership(singleton, owner_identity, previous_term, previous_index)
ReleaseLeadership(singleton, owner_identity, term, index)
StepDown(singleton, owner_identity, reason)
```

Fencing token:

```text
fencing_token = encode(term, log_index)
```

The Raft backend must use a committed voter set for quorum. It must never compute
majority from a node-local `alive_nodes` vector. During membership changes, joint
consensus or an equivalent safe transition is required before the new voter set
can issue leadership.

## 11. State Machine

```text
Standby
  -> Campaigning
  -> Active
  -> Renewing
  -> SteppingDown
  -> Standby

Standby
  -> NoQuorum
  -> Standby

Active
  -> Fenced
  -> SteppingDown
  -> Standby
```

| State | Meaning | Mutating Work |
|-------|---------|---------------|
| `Standby` | Local node is not owner. | Reject or forward. |
| `Campaigning` | Backend acquisition in progress. | Reject. |
| `Active` | Valid lease held locally. | Accept with token. |
| `Renewing` | Renewal in progress before deadline. | Accept until safety deadline. |
| `SteppingDown` | Lease lost or release requested. | Reject new mutations, drain old work. |
| `NoQuorum` | Cannot prove ownership. | Reject. |
| `Fenced` | Backend reports a higher owner/token. | Reject, audit, invalidate local state. |

The transition from `Renewing` to `Active` only happens after successful backend
validation. If the safety deadline passes before validation, the node must step
down even if the backend may later respond.

## 12. Membership And Partition Semantics

### 12.1 Membership Epoch

`ClusterFailureModel` owns local state transitions and exposes a membership
epoch. The leadership backend stores the epoch used to grant leadership. A node
must not acquire leadership with a stale epoch.

### 12.2 Partition Handling

Partition behavior:

- If the owner can reach the backend and renew, it remains owner.
- If the owner cannot reach the backend before the safety deadline, it steps
  down.
- If a minority partition can reach peers through gossip but not the backend, it
  cannot elect a production owner.
- If another node obtains a higher backend token, stale owners are fenced.

This intentionally prioritizes control-plane safety over singleton availability.

### 12.3 Discovery Integration

Gossip membership feeds the failure model. The failure model feeds leadership
eligibility. Gossip piggyback may carry diagnostic leadership hints, but it is
not authoritative for production ownership.

## 14. Failure Semantics

| Condition | Local Action | Failure |
|-----------|--------------|---------|
| Backend request timeout | Retry until renew deadline. | `LeadershipBackendTimeout` |
| Backend unavailable past deadline | Step down. | `LeadershipUnavailable` |
| Owner key changed to another node | Fence local owner. | `FencingTokenStale` |
| Membership epoch stale | Rejoin before campaigning. | `StaleMembershipEpoch` |
| Wrong cluster id | Reject identity. | `NodeQuarantined` or `ClusterIdMismatch` |
| Lease lost while active | Drain singleton. | `LeadershipLost` |
| Mutating command has old token | Reject command. | `FencingTokenStale` |

If new failure reasons are added, they should map to `FailureEnvelope`, DLQ
records where a user message is rejected, metrics counters, and structured logs.

### Logs And Audit

Every leadership transition logs:

- singleton name,
- old state,
- new state,
- owner node id,
- membership epoch,
- fencing token,
- backend term/revision,
- reason.

Ownership changes should also emit audit records because they affect cluster
metadata authority.

### CLI/Admin

Recommended CLI commands:

```text
/cluster leadership
/cluster leadership <singleton> show
/cluster leadership <singleton> step-down
/cluster leadership backend
/cluster leadership audit <singleton>
```

The admin API should expose equivalent read-only endpoints before exposing
operator mutation endpoints.

## 16. Testing Strategy

### Unit Tests

- `LeadershipLease` comparison and token ordering.
- Fake backend acquire, renew, release, current-owner, and watch behavior.
- State-machine transitions for `Standby`, `Campaigning`, `Active`,
  `Renewing`, `SteppingDown`, `NoQuorum`, and `Fenced`.
- Token rejection for stale, missing, and wrong-singleton tokens.
- Membership epoch rejection.

### Actor Wrapper Tests

- `ClusterLeadershipManagerActor` converts backend grant to singleton activation.
- Lease loss triggers `Active -> Draining -> Standby`.
- Renewal timeout triggers step-down before accepting further mutations.
- Backend callbacks do not run under the core mutex.

### Integration Tests

- `ActorSystem::enable_cluster()` wires discovery events into
  `ClusterFailureModel`, then leadership eligibility.
- `ShardCoordinatorActor` refuses rebalance without a valid leadership token.
- Route invalidation happens after leader loss and node down.
- Cluster mode disabled keeps single-node behavior unchanged.

### Partition And Chaos Tests

- Five-node cluster split 3/2 with external backend reachable only from the
  minority: minority may hold leadership only if it can renew with the backend;
  other partitions must reject mutations.
- Owner loses coordinator reachability: steps down before lease safety deadline.
- Old owner receives delayed mutating command after new token: rejects with
  `FencingTokenStale`.
- Node restart with higher incarnation fences old lease identity.
- Backend watch compaction forces linearizable owner read before reactivation.

## 17. Migration Plan

1. **Document production contract**: land this design and mark local/gossip
   strategies as non-production ownership modes.
2. **Add core types and fake backend**: implement `LeadershipLease`,
   `ILeadershipBackend`, fake deterministic backend, and core state machine.
3. **Integrate singleton manager**: make production singleton activation consume
   leases instead of directly self-promoting from `ISingletonElection`.
4. **Add etcd backend**: external coordinator implementation with bounded
   blocking executor, TLS config, and watch support.
5. **Gate shard coordinator mutations**: require current leadership token for
   shard ownership updates and rebalance.
6. **Add Consul backend**: optional deployment backend after etcd proves the
   interface.
7. **Add internal Raft backend**: future backend with the same public contract.

## 18. Acceptance Criteria

1. A production-configured singleton cannot become active without a backend
   lease.
2. Fencing tokens are backend-issued and monotonically ordered for each
   singleton.
3. Mutating shard-coordinator commands reject stale tokens.
4. Loss of backend reachability causes owner step-down before the safety
   deadline.
5. Node restart and incarnation conflicts fence old ownership.
6. External coordinator calls do not block scheduler or event-loop paths.
7. CLI, metrics, logs, and audit records expose leadership owner, token, backend
   revision, and transition reason.
8. Local election strategies remain available only as explicit non-production
   modes.

## 19. Open Implementation Decisions

These choices are intentionally left to the implementation plan:

- Exact etcd client dependency and transport wrapper.
- Whether Consul support lands in the first external-coordinator milestone or a
  follow-up.
- Exact protobuf/control-message layout for leadership lease propagation.
- Whether token validation lives directly in `ShardCoordinatorCore` or a small
  reusable `LeadershipGuard`.

None of these change the production contract above.
